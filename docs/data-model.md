# Data model

PostgreSQL 16, managed with [Drizzle ORM](https://orm.drizzle.team/). The
schema source of truth is [`web/src/server/db/schema.ts`](../web/src/server/db/schema.ts);
SQL migrations generated from it are committed under
[`web/drizzle/`](../web/drizzle/) and applied when the web container starts.

All primary keys are UUIDs generated by Postgres (`gen_random_uuid()`), so
user IDs in logs are internal identifiers, never provider IDs or emails.
All timestamps are `timestamptz`.

## Auth.js tables

| Table | Columns | Notes |
|-------|---------|-------|
| `users` | `id`, `name`, `email`, `email_verified`, `image`, `created_at` | `email` is **not unique**: two provider accounts with the same email are two users unless explicitly linked. |
| `accounts` | `user_id`, `type`, `provider`, `provider_account_id`, token columns | Primary key `(provider, provider_account_id)`. The adapter wrapper stores only the identifying columns; OAuth access, refresh, and ID tokens are discarded after sign-in because the app never calls provider APIs on the user's behalf. |
| `sessions` | `session_token`, `user_id`, `expires` | Database sessions; 30 day rolling expiry. |
| `verification_tokens` | `identifier`, `token`, `expires` | Required by the adapter interface; unused because there are no email or magic-link sign-ins. |

## Application tables

```
users 1---* decks 1---* cards 1---* card_progress *---1 users
                                 \--* review_log    *---1 users
users 1---* upload_events
```

### `cards`

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid PK | |
| `deck_id` | uuid FK `decks.id` ON DELETE CASCADE, not null | Ownership is `decks.user_id`. |

### `card_progress`

FSRS scheduling state per user per card.

| Column | Type | Notes |
|--------|------|-------|
| `card_id` | uuid FK `cards.id` ON DELETE CASCADE | PK part 1 |
| `user_id` | uuid FK `users.id` ON DELETE CASCADE | PK part 2 |
| `due` | timestamptz not null | |
| `stability`, `difficulty` | double precision | |
| `reps`, `lapses` | integer | |
| `state` | smallint | 0 New, 1 Learning, 2 Review, 3 Relearning (ts-fsrs `State`) |
| `last_review` | timestamptz | |
| `scheduled_days`, `learning_steps` | integer | Extra fields ts-fsrs v5 needs to resume a card exactly. |

Index: `(user_id, due)`.

A card with no `card_progress` row is new.

### `upload_events`

Used for rate limiting and basic operational metrics. Contains no file names
or content.

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid PK | |
| `user_id` | uuid FK ON DELETE CASCADE | |
| `created_at` | timestamptz | |
| `bytes` | integer | |
| `status` | text | `accepted`, `rejected`, `failed` |

Index: `(user_id, created_at)`.

Rate limits are 10 uploads per rolling hour and 100 per rolling day per user,
counting every event regardless of status, so rejected files still count.
Exceeding a limit returns HTTP 429 with `Retry-After` set to the seconds until
the oldest event in the window expires.

## Database roles

Use two roles. The app never runs DDL at runtime.

| Role | Used by | Privileges |
|------|---------|------------|
| `quizme_migrator` | migration step at container start (`MIGRATION_DATABASE_URL`) | Owns the database and the `public` and `drizzle` schemas. Runs `CREATE`/`ALTER`/`DROP`. |
| `quizme_app` | the running web server (`DATABASE_URL`) | `CONNECT`; `USAGE` on `public`; `SELECT, INSERT, UPDATE, DELETE` on tables; no `CREATE` on any schema; not a superuser; does not own any table. |

[`web/db/roles.sql`](../web/db/roles.sql) creates both roles. It takes the
passwords as psql variables so nothing secret is stored in the file:

```sh
psql "$ADMIN_URL" -v migrator_password="$MIGRATOR_PW" -v app_password="$APP_PW" \
  -v db_name=quizme -f web/db/roles.sql
```

Default privileges are set `FOR ROLE quizme_migrator`, so tables created by
future migrations are automatically granted to `quizme_app`.

If `MIGRATION_DATABASE_URL` is not set, the container runs migrations with
`DATABASE_URL`. That is convenient for a laptop but means the runtime role
needs DDL rights, so production deployments should always set both.

## Account deletion

`/account` has a "Delete my account" action. It deletes, in one transaction,
the user's review log, progress, cards, decks, upload events, sessions,
accounts, and finally the user row. Foreign keys also cascade, as a second
line of defense. The session cookie is cleared afterwards.
